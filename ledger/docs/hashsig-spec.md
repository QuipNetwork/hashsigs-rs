# SHRINCS Ledger signer contract

Specification revision 1, 2026-10-12. Target protocol: **2**.

This document defines the first capacity-four stateful signer for Nano Gen5.
It describes the complete intended signer. The checked-in app is now version
0.2.0, protocol 2: derivation, full hybrid key creation, authenticated storage,
reload, public queries, and verification are implemented. Signing commands and
leaf reservation remain unimplemented. Capabilities are `0x00000003`, never the
signing bit. Section 8 separates emulator evidence from pending hardware gates.
The [verification baseline](../README.md) remains regression coverage.

The decisions below are fixed for this experiment. Any incompatible derivation,
storage, or wire change must revise this document and the corresponding version;
never silently reinterpret an existing key or record. Hardware-dependent
acceptance evidence is listed separately in section 8.

## 1. Scope, identity, and limits

The reference is `hashsigs-rs` 0.2.1-rc9 at
`2779dc8ae91bba02ef10efeaa9d1e88712f836ae`. Device integration stays under
`ledger/` and uses existing core public APIs with `default-features = false`
and features `alloc,profile-256s-sha2,heap-buffers`.

| Property | Contract |
| --- | --- |
| Target | Nano Gen5, `apex_p`, API 26, target ID `0x33400004` |
| Profile | `shrincs-256s-sha2` |
| Profile ID | `807de98ac65ab9f03289950d1878e5ec5261f162af5593ccba2f1709c793c2bb` |
| Scheme hashes | SHA-256, 32-byte outputs; Keccak-256 for commitments and message domains |
| Stateful primitive | UXMSS unbalanced tree with WOTS-C; 64 chains, base 16, at most 15 steps per chain, target sum 480 |
| Stateful capacity | Exactly 4; leaves 1–4, exhausted next-leaf value 5 |
| WOTS-C grinding | First successful counter in `0..2^24`; failure consumes any reserved leaf |
| Stateless parameters | Height 64, 8 layers, 22 FORS trees of height 14, FORS-C counter limit `2^24`, lifetime signature limit `2^20` |
| Device operations | Full hybrid key generation, stateful digest signing, existing stateful verification |
| Stateless signing/verification | Unsupported in protocol 2; the real stateless public root is nevertheless required during key generation |
| Key slots | One hybrid identity per installation; no host-selected account/path, import, export of secrets, reset, replacement, or rotation command |
| Signed input | Exactly one opaque 32-byte digest; no streamed message or `ActionContext` signing |
| Verification input | Existing 4096-byte maximum envelope |
| Public-key output | 480-byte canonical `PublicKey::to_bytes()` ABI encoding |
| Stateful signature output | Canonical envelope, `2752 + 32 * leaf` bytes: 2784, 2816, 2848, 2880 |
| Output chunks | 1–200 bytes per successful read |
| Secret serialization | 264-byte `Keys::to_bytes()`, used internally in the authenticated NVM record only |
| NVM | One 512-byte payload plus a separate 512-byte commit marker; 1024 bytes before any additional linker padding |

Parameters come from [the profile](../../src/profiles/p256s_sha2.rs),
[UXMSS](../../src/shrincs/uxmss.rs), and [WOTS-C](../../src/wots_c/mod.rs).
This is the existing SHRINCS 256s construction and its security intent, with a
small supported stateful capacity. It is not an XMSS or SLH-DSA conformance
claim or a new security analysis. The app KDF and persistence policy are
experimental integration choices. An unbalanced authentication path has one
node per leaf index; the signature grinding counter is not that index.

Keep the pinned builder and toolchain in [Dockerfile](../Dockerfile), Rust SDK
1.36.1, Speculos 0.27.0, Ragger 1.47.3, and the app/host lockfiles. Portable core
hashes remain the initial scheme implementation. SDK HMAC and derivation are
used for the app key hierarchy; this does not introduce a core hash backend.

## 2. Device derivation and key creation

### Namespace and KDF

Use the wallet's active seed/passphrase through the OS **SLIP-0021 symmetric
derivation** facility. The app must never receive that seed from the host.
The sole first-level label is ASCII `quip.network/SHRINCS/v1` (23 bytes).
Authorize that label at installation with the SLIP-21 permission bit `0x08`;
grant no elliptic-curve derivation or master-seed access permission. This is
a local experimental namespace, not a registered BIP44 coin path.

Mathematically, for the active wallet seed `S`:

```text
M      = HMAC-SHA512(key="Symmetric key seed", message=S)
N      = HMAC-SHA512(key=M[0:32], message=0x00 || "quip.network/SHRINCS/v1")
K_app  = N[32:64]
G      = 32 fresh random bytes generated by the device after creation approval
P      = the 32-byte profile ID above
seed   = HMAC-SHA256(K_app, "shrincs-ledger/keygen/v1\0" || P || G || u32be(4))
K_state = HMAC-SHA256(K_app, "shrincs-ledger/state-mac/v1\0" || P || G)
```

The first two derivations follow [SLIP-0021][slip21]; the two HMAC-SHA256
expansions are this app's contract. Quoted strings are their exact ASCII bytes.
`\0` denotes exactly one zero byte. `||` is concatenation; slices are half-open.
No other terminators, length prefixes, or Unicode transformations are inserted.
`G` is public; `K_app`, `seed`, and `K_state` are secret.

Use an app-local C shim around the pinned C SDK's
`os_derive_bip32_with_seed_no_throw(HDW_SLIP21, CX_CURVE_SECP256K1, ...)`.
The curve argument is the API convention for this symmetric mode, not an EC
key derivation. Supply a 4-byte-aligned buffer containing `0x00 || label`, pass
the **24-byte** path length, and use a 64-byte zero-initialized output buffer.
Reserve at least 96 bytes for the path buffer because the legacy firewall
annotation bounds it as `4 * pathLength`; padding is not part of the label.
Check the returned status before using **output bytes 0–31 as `K_app`**. The
syscall exports the symmetric key at the start of its output, unlike the
64-byte SLIP node in the mathematical definition. Ledger's
[symmetric-key helper][ledger-symmetric] demonstrates this convention.

SDK 1.36.1's Rust `SeedDerive` trait provides EC paths, not a suitable typed
SLIP-21 wrapper. Keep the C exception boundary inside the shim, and erase its
buffers on every return. The SDK interprets an empty `curve` list as mask `0xff`.
Use `curve = ["slip21"]`, `path = []`, and
`path_slip21 = ["quip.network/SHRINCS/v1"]` to produce mask `0x08`.
The ELF test checks the complete emitted derivation TLV. The inspected `ledgerblue`
loader accepts `--path_slip21 quip.network/SHRINCS/v1`; implementation must
inspect the emitted derivation TLV and validate the narrow permissions on
Gen5. Do not enable unrestricted derivation to work around a load failure.

Generate `G` with `ledger_device_sdk::random::rand_bytes`, backed by
`cx_rng_no_throw`. The pinned API has no error return. An OS/RNG failure must
abort; an all-zero result is rejected without creating a key. This check is
not an entropy test. Acceptance relies on the device RNG, not host randomness.
Use a separate RNG call for the boot nonce in section 5.

### Creation, reload, and recovery identity

`CREATE_KEY` is available only in `EMPTY` state with no active operation:

1. Validate the fixed profile/capacity, then show an explicit creation review:
   experimental SHRINCS, capacity four, and loss of this app state means a new
   public key. Rejection leaves storage untouched.
2. Generate `G`, derive the secrets, and run
   `ShrincsSigner::keygen::<SelectedProfile, NUM_CHAINS, NUM_LAYERS>(&seed, 4)`.
   Compute both real roots; placeholder stateless material is forbidden.
3. Check the returned key/public bundle and commitment agree. Create the record
   in section 4 with `next_leaf = sequence = 1` and zero stateless uses.
4. Commit and read back that record before publishing success or the new public
   identity. Display the new commitment on the device after successful creation.

The key identifier is the full 32-byte hybrid commitment `C`, not `G`, a slot
number, or an abbreviated fingerprint. A successful record is the source of
all subsequent public-key responses. A lost creation response is reconciled
with `GET_STATE` and `GET_PUBLIC_KEY`; repeating `CREATE_KEY` cannot replace an
existing key. Failure before any NVM write leaves `EMPTY`; failure after a
write attempt locks the app until restart and the recovery rules below apply.

After restart, authenticate and validate the stored record before decoding
`Keys::from_bytes::<SelectedProfile>`. That API is a structural parse, not
root re-derivation; it is used only for this device-created, authenticated
record. No untrusted key import path is exposed. Rebuild `PublicKey` from its
stored public components and recompute `C`. Full key generation need not be
repeated on every launch. Check both stored copies of the next leaf agree.

The secret record remains inside app NVM protected by LedgerOS isolation.
Its MAC provides integrity and wallet binding, not encryption. Erase transient
derivation material, serialized-key copies, and keyed HMAC contexts on success,
error, rejection, cancellation, and normal exit. Use zeroizing wrappers for
secret buffers; do not rely on panic unwinding to erase them. Abrupt power loss
does not execute Rust destructors.

There is no seed-only restoration of the old stateful identity. Reinstall,
reset, or deliberate abandonment of a locked/exhausted key requires explicit
creation with fresh device randomness. Even with the same mnemonic, this
produces a new `G` and commitment. Another device does likewise. The app never
accepts a host-supplied old `G` or counter. An existing on-chain account does
not automatically adopt this new identity; account rotation/recovery is outside
protocol 2. Switching the wallet seed/passphrase makes the old MAC unverifiable;
returning to the matching wallet can reload an otherwise intact record.

## 3. Message and signature contract

Protocol 2 signs a caller-supplied digest `D[32]` as opaque data. It does not
claim to know the originating message, its length, its hash algorithm, or its
transaction meaning. There is no host-supplied context, original-message
length, or human-readable description to display as authenticated content.

The final review must show the experimental scheme/profile, the full commitment
(scrolling is acceptable), **Opaque digest, 32 bytes**, all 64 digest hex digits,
and the candidate leaf/remaining capacity. The frozen bytes shown are the
bytes signed. The user must explicitly approve every new signing request.

Use `ShrincsSigner::sign_stateful_adapter_at_leaf` with the internally reserved
leaf, then `encode_stateful_envelope`. This calls the existing commitment-bound
adapter, which signs:

```text
op = Keccak256(ASCII("shrincs-verify-stateful"))
message = Keccak256(op || u32be(2) || C || D)
```

Here `2` is the SHA-256 scheme-suite ID, not the APDU protocol version.
Definitions are in [dispatch.rs](../../src/shrincs/dispatch.rs) and
[signer.rs](../../src/shrincs/signer.rs). Do not pass `D` directly to a raw
signing primitive. This format preserves existing ERC-7913 adapter verification;
adding a new app context or streamed-message prehash would require a separately
specified signing mode.

The commitment is the existing:

```text
C = Keccak256("shrincs-public-key/" || "shrincs-256s-sha2" ||
              stateful_public_key[68] || stateless_pk_seed[32] ||
              stateless_hypertree_root[32])
stateful_public_key = stateful_pk_seed[32] || root[32] || u32be(4)
```

Export `PublicKey::to_bytes()` and `encode_stateful_envelope` byte-for-byte,
including their canonical Solidity ABI offsets, padding, and outer tuple.
Do not substitute the packed 164-byte public bundle for the 480-byte ABI blob.
See [key.rs](../../src/shrincs/key.rs) and
[signature.rs](../../src/shrincs/signature.rs). At leaf `i`, the authentication
path has exactly `i` nodes and the envelope length is `2752 + 32*i`.

Signing is deterministic for fixed key, leaf, and digest, including the core's
PRF-derived randomizer and first winning grinding counter. That is a fixture
property, not permission to reuse a leaf. A fresh request always consumes a
new leaf even if its digest equals a previous one. Only reads of the same
already-completed live request may replay signature bytes.

## 4. Persistent record and durable reservation

### Logical payload, record format 1

Serialize explicitly; never write a Rust struct's native layout or pointers.
Integers below are unsigned big-endian. Offsets use half-open byte ranges.

| Bytes | Field | Valid value |
| --- | --- | --- |
| 0–8 | Magic | ASCII `SHRINCS2` |
| 8–10 | Record format `u16` | 1 |
| 10–12 | Payload length `u16` | 512 |
| 12–20 | Commit sequence `u64` | 1 on creation; increment once per reservation; no wrap |
| 20–21 | Record kind `u8` | 1: initialized key, including exhausted keys |
| 21–22 | Derivation version `u8` | 1: section 2 |
| 22–24 | Reserved | Zero |
| 24–56 | Profile ID | `P` |
| 56–88 | Generation ID | `G`, nonzero |
| 88–120 | Key ID | Recomputed commitment `C`, nonzero |
| 120–124 | Stateful capacity `u32` | 4 |
| 124–128 | Authoritative next leaf `u32` | 1–5 |
| 128–132 | Stateless uses reserved `u32` | 0 in this version |
| 132–136 | Stateless lifetime limit `u32` | 1048576 |
| 136–400 | Secret key bytes | Core 264-byte `Keys::to_bytes()` |
| 400–480 | Reserved | Zero |
| 480–512 | Record MAC | `HMAC-SHA256(K_state, payload[0:480])` |

Authenticate with constant-time MAC comparison before using any secret-key
fields. Before deriving `K_state`, only parse bounded fixed header fields and
`G`. Reject unknown versions, nonzero reserved bytes, wrong lengths/profile,
out-of-range counters, or inconsistent duplicated fields. In this version
`sequence == next_leaf` because creation and stateful reservations are the only
mutations. The capacity and next leaf inside the serialized core key must equal
the record values. Recompute the commitment from its public components.
Authentication failure, unavailable derivation, or a failed structural check
permits no signing and no repair to leaf one.

Stateless uses are stored now to make the intended lifetime policy explicit.
This version cannot increment them or sign statelessly. A later protocol must
reserve each use durably before signing, burn failed reservations, and preserve
the budget if the stateless key survives a stateful reset. Its storage changes
require an explicit migration/version decision.

### Physical layout and write order

Use two **separate, 512-byte-aligned NVM blocks**: `marker[512]` and
`payload[512]`. The installed initial contents of both are all zero. The sole
committed marker is 512 bytes of `0xA5`; all other patterns are uncommitted.
Use app-local storage over SDK `NVMData`/`AlignedStorage` and `nvm_write`, with
explicit serialization, alignment, bounds, and PIC access. Do not keep a
borrow of the stored data across an update.

The chosen policy uses one record and **no fallback to an older copy**. The
pinned Rust [NVM implementation][rust-nvm] exposes generic `AtomicStorage`, but
that abstraction does not implement this application's fail-closed recovery
policy. A journal that preserves availability can be designed later without
weakening monotonic leaf allocation.

For creation or a leaf reservation:

1. Prepare and authenticate the complete candidate payload in RAM. On signing,
   let `i = next_leaf`; reject `i > 4`, then put `i + 1` in both next-leaf fields
   and increment sequence. Keep `i` only in the immutable live request.
2. Write an all-zero marker and read it back exactly. No payload byte may be
   written until invalidation completes.
3. Write the candidate payload, read it back, check exact equality, and validate
   its MAC/structure while the marker is still invalid.
4. Write the all-`0xA5` marker, read it back, and revalidate the whole committed
   record against the candidate. Only now does the operation consider it durable.
5. For creation, publish the public identity. For signing, invoke the at-leaf
   signer at reserved leaf `i`, with the updated record already authoritative.

An NVM exception, failed readback, or uncertain write result locks the running
app, erases its transient signing material, and releases no signature. Never
attempt an automatic repair write. A failed core sign, allocation, encoding,
verification, or transport operation after successful reservation burns `i`.
Do not decrement, reclaim, or auto-advance a stale in-memory counter. Construct
the candidate core key using its public constructors with the updated next
leaf; the cryptographic call is always the explicit at-leaf adapter.

Before marking output ready, require its canonical size and verify it with
`ShrincsVerifier::verify(C, D, envelope)`. A failed self-check releases no bytes
and clears the live request; it does not restore the leaf. Independent host
verification is still required and is not replaced by this self-check.

### Recovery and its limits

| Stored condition at launch | Result |
| --- | --- |
| Both blocks exactly all zero | `EMPTY`; only explicit creation can establish a new identity |
| Exact committed marker and authenticated, consistent payload with next leaf 1–4 | `READY` |
| Same, with next leaf 5 | `EXHAUSTED`; public data stays readable |
| Any other condition, including invalid marker with a nonzero payload | `LOCKED`; no key recreation, signing, or counter repair |

A restart after a completed reservation loads the advanced counter, whether
or not the signature was computed or delivered. A torn write can permanently
retire this key: even an intact older payload is not trusted after marker
invalidation. Losing availability in this case is intentional for the first
experiment. A later operator-directed reinstall may create a fresh identity;
it cannot recover the previous signing history.

The power-interruption model assumes ordered SDK writes, durable completed
writes, and marker/payload erase isolation. Readback is a consistency check,
not proof of physical durability. Ledger's [storage documentation][ledger-nvm]
requires SDK writes but does not establish this entire transaction contract.
Confirm actual erase granularity and ordering on the pinned Gen5 OS before
enabling hardware signing; increase alignment/separation if 512 bytes is
insufficient. Test interruptions at each write and readback boundary.

A MAC or commit sequence does **not** detect replay of an entire older valid
record. Arbitrary NVM snapshot restoration, a malicious app update, and
physical fault attacks are outside this experiment's rollback guarantee.
There is no host backup/import feature. Upgrade continuity is unsupported
until preservation/migration and interruption behavior are specified and
tested; migration must never reset counters for the same identity.

## 5. APDU protocol 2

### Framing and discovery

Retain CLA `E0`, short APDUs with at most 255 request-data bytes, and the
[protocol-1 commands](../README.md#protocol-version-1). All new commands have
P1=P2=0. Wrong P1/P2 is rejected; integers are big-endian. Request lengths are
exact, with no optional trailing fields. Error replies have no data.

`GET_PROFILE` (`05`) keeps its layout but reports protocol byte **2**. Hosts
must require protocol 2 and matching profile before using signer commands.
`GET_VERSION` reports app `0.2.0`. Do not advertise a capability merely because
it is specified; this implementation advertises verification and key management.

New `GET_INFO` (`06`, empty request) returns this **69-byte** structure:

```text
protocol:u8=2 | spec_revision:u16=1 | capabilities:u32 |
profile_id:[32] | boot_nonce:[16] | capacity:u32=4 |
digest_length:u16=32 | max_envelope:u16=4096 | public_key_length:u16=480 |
max_output_chunk:u16=200 | record_version:u16=1
```

Capability bits are 0: stateful verification, 1: full device key creation and
public/state queries, 2: persistent stateful digest signing. A complete first
signer reports `0x00000007`; a key-creation-only build reports `0x00000003`.
All other bits are zero. Unsupported commands return `6D00`; unsupported
signing modes return `6A81`. No stateless capability is defined in this revision.

Generate a nonzero 16-byte boot nonce once per app launch using the device RNG.
If that fails, disable key creation/signing for that run rather than substitute
a constant. A signer request token is `boot_nonce[16] || request_counter:u32`.
Counters start at 1, increase on every accepted `SIGN_BEGIN`, are never reused
within the boot, and refuse new requests on overflow. Check all 20 token bytes.
Tokens prevent accidental stale-session use; they do not authenticate the host.
Existing verification upload IDs remain their separate protocol-1 `u32` IDs.

### Commands

Notation: `C` is the selected key ID, `P` the profile ID, `T` a 20-byte signer
token, `i` a leaf index, `off` a byte offset, and `n` a requested byte count.

| INS | Name | Exact request | Success data |
| --- | --- | --- | --- |
| `06` | `GET_INFO` | Empty | 69 bytes above |
| `30` | `CREATE_KEY` | `P[32] || capacity:u32=4` (36 bytes) | `C[32] || public_length:u16=480` (34 bytes), after approval and durable creation |
| `31` | `GET_PUBLIC_KEY` | `C[32] || off:u16 || n:u8` (35 bytes) | `C[32] || total:u16=480 || off:u16 || n:u8 || bytes[n]` |
| `32` | `GET_STATE` | Empty | 110 bytes below |
| `40` | `SIGN_BEGIN` | `P[32] || C[32] || mode:u8=0 || input_kind:u8=0 || input_length:u16=32 || D[32]` (100 bytes) | `T[20]` |
| `41` | Reserved for future message updates | Unsupported | `6D00`; no streaming in this revision |
| `42` | `SIGN_FINALIZE` | `T[20]` | `T[20] || i:u32 || total:u16` (26 bytes), after review, reservation, signing, and self-check |
| `43` | `READ_SIGNATURE` | `T[20] || off:u16 || n:u8` (23 bytes) | `T[20] || i:u32 || total:u16 || off:u16 || n:u8 || bytes[n]` |
| `23` | `CANCEL` | Empty, as in protocol 1 | Empty; clears the current transient operation/output, never persistent reservations |

`mode=0` means stateful; `input_kind=0` means opaque digest. A different
profile, capacity, or input length is rejected before user interaction or state
mutation. A mismatched key ID never selects or creates another key.

For both chunk reads require `1 <= n <= 200`, `off < total`, and
`off + n <= total` with checked arithmetic. Return exactly `n` bytes; reject
rather than silently shorten an invalid range. Public-key responses are at most
237 bytes and signature responses at most 229, excluding status bytes. The
host validates every echoed identity/token, leaf, length, offset, and count.
An incomplete output or `9000` without the required data is not success.

`GET_STATE` layout (110 bytes):

```text
key_state:u8 | C:[32] | G:[32] | capacity:u32 | next_leaf:u32 |
stateless_uses:u32 | stateless_limit:u32 | sequence:u64 |
operation:u8 | signer_token:[20]
```

Key states: `0=EMPTY`, `1=READY`, `2=EXHAUSTED`, `3=LOCKED`. In `EMPTY` or
`LOCKED`, every key field from `C` through `sequence` is zero, not untrusted
record content. For a validated key, capacity is 4, remaining stateful capacity
is `5 - next_leaf`, stateless uses are 0 and limit is `1048576`. This stored
limit does not advertise an implemented stateless operation.

Operations: `0=IDLE`, `1=VERIFY_UPLOAD`, `2=SIGN_PENDING`, `3=SIGN_READY`.
The token is nonzero only for the latter two. `GET_STATE` returns public fields
only and validates persistent state before reporting key counters. Review,
keygen, and signing computation are busy phases, not pollable background jobs.

### Session rules, approval, and retries

Only one verification upload, pending signing request, or completed signature
may occupy the app at a time. `CREATE_KEY`, `BEGIN_VERIFY`, `SIGN_BEGIN`, and
SHA-256 smoke operations require `IDLE`. Identity/profile/info/state queries
may run in stable non-busy states. During review or computation, accept no
competing command that can alter the approved request; if the SDK delivers one,
reject it with `6986` without replacing the pending command/response context.
An implementation unable to preserve that context must abort the original
operation without releasing output, applying the same reservation rules.

`SIGN_BEGIN` validates and copies the entire request into immutable app-owned
memory, allocates `T`, and enters `SIGN_PENDING`. It does not reserve a leaf.
Exhaustion is checked here and again before reservation. The host cannot
select a leaf, grinding counter, entropy, generation ID, or private key.

`SIGN_FINALIZE(T)` reviews the frozen request and candidate leaf. Rejection
returns `6985`, erases the request, and leaves the counter unchanged. Approval
performs the durable reservation in section 4 before any signature computation.
Success enters `SIGN_READY`; signing keys and scratch secrets are erased while
the public envelope and request metadata remain in RAM.

An exact repeated `SIGN_FINALIZE(T)` in `SIGN_READY` returns the same metadata
without another approval, signature calculation, or reservation. Repeated or
out-of-order valid `READ_SIGNATURE` calls return the same stored bytes. Reading
the last chunk does not discard the result. A new begin requires `CANCEL`
first; it cannot replace a pending request or completed result implicitly.
Wrong tokens and invalid reads leave a stable pending/result session intact.

`CANCEL` is idempotent in stable states and frees transient buffers. It cannot
interrupt a blocking core call or restore a reserved leaf. Device rejection or
app exit abandons review; exit/reset discards every live request and output.
A failure after reservation destroys the request rather than allowing signing
to be retried at that leaf. Query persistent state before requesting another.

There is no device-side idle expiry in revision 1: pending/result sessions live
until cancellation or app exit. Host defaults are 10 seconds for short APDUs,
300 seconds for `CREATE_KEY`, and 180 seconds for `SIGN_FINALIZE`, including
human review. A host timeout is not a cancellation or evidence of nonexecution.
Stop sending APDUs until the device is responsive. Then query `GET_INFO` and
`GET_STATE`: retry finalize/read only for the same boot and a reported
`SIGN_READY` token. For `SIGN_PENDING`, cancel and begin again; for idle or a
new boot, the old output is unavailable. Never automatically resend a signing
operation after a lost response. Bound USB tests with the existing thread
watchdog; this host watchdog does not enforce device execution deadlines.

### Status words

| SW | Meaning and state effect |
| --- | --- |
| `9000` | Success; for verification, still inspect the protocol-1 verdict byte |
| `6985` | User rejected; no reservation for that request |
| `6986` | Busy, wrong operation state, absent session, or disallowed create; no new reservation |
| `6984` | Persistent state locked, invalid, or incompatible; signing unavailable |
| `6A80` | Malformed data, wrong profile/capacity/digest length, invalid token or read range |
| `6A81` | Unsupported signing mode/input kind |
| `6A84` | Stateful capacity exhausted; no new reservation |
| `6A88` | No such selected key (`GET_PUBLIC_KEY`/`SIGN_BEGIN`) |
| `6A86` | Wrong P1/P2 |
| `6D00` | Unknown or unavailable instruction |
| `6581` | Storage operation failed or readback uncertain; running app locks |
| `6F00` | Internal/keygen/signing failure; a reservation may already be consumed |
| `6E00`, `6E03` | Existing SDK wrong-CLA and malformed-transport errors |

Validate framing/instruction/P1/P2 and exact payload shape before side effects.
For well-formed key operations, a locked record takes precedence over key-ID
or exhaustion checks. Hardware faults can terminate the app without any SW;
the host must reconcile state exactly as for a lost response.

## 6. Resource and timing acceptance bounds

These are initial **lab acceptance targets**, not measured signing results or
changes to cryptographic parameters. Measure them before declaring the signer
usable; revise the contract explicitly if feasibility requires different bounds.

| Resource/operation | Initial acceptance bound |
| --- | --- |
| Heap | Keep 20 KiB allocation; measured peak at most 18 KiB, including output, codec temporaries, and UI |
| Stack | At least 4 KiB measured headroom in the actual linked SRAM layout under the worst tested operation |
| NVM | 1024-byte logical physical layout above; record actual alignment/padding and erase units |
| Output held in RAM | At most one 2880-byte signature envelope; avoid a concurrent verification upload |
| Full key generation | At most 120 seconds after approval, including durable creation |
| Stateful signing | At most 10 seconds after approval, including reservation, encoding, and self-verification; record all four leaves and grinding variability |
| Public export/signature download | Measure separately from cryptography and human approval; 200-byte reads |

Instrument actual Gen5 heap/stack high-water marks. A successful build or APDU
chunking does not prove the core's temporary allocations fit. Trace persistent
writes: creation and each reservation each perform marker invalidation, payload
write, and marker commit; reads/rejection/cancel perform no NVM writes.
Do not delay counter writes until exit to save flash cycles.

The implementation must preserve SDK event/watchdog servicing during long
operations. The core APIs are synchronous; whether full key generation meets
that requirement on hardware is unproven. If it does not fit the memory/time/
watchdog bounds, keep that capability unavailable and record the failure.
Do not omit the stateless root, offload secret computation, or lower scheme
parameters to obtain a passing result. Reusable buffers or incremental core
work require separate review and vector validation.

## 8. Acceptance evidence and remaining device assumptions

The key-creation/reload implementation is complete in software; it does not
complete the signer or the full plan's M1–M6 acceptance criteria.

Recorded on 2026-10-12: **61 Speculos/ELF tests passed in 33.17 s**, with all
three crates' formatting checks passing. The normal ELF SHA-256 is
`8a1699d36e87f0d392fa147cd4ad22146f0a3baf092b9d6755ec660cf6cfe5bb`.
Eight native storage tests pass, covering all 1,539
write-prefix failure positions and corruption/semantic/exhaustion checks.
Emulator key-management coverage includes full hybrid public-key agreement,
approval/rejection, actual process restart with saved NVM, wrong-seed locks,
payload/tag/marker corruption, lost creation response, and competing APDUs.
The ELF test checks mask `08`, the sole SLIP21 label, and two separate aligned
512-byte blocks. Review uses an app event loop that replies `6986` to competing
APDUs without freezing touch input or changing the original request.

The [memory run](../README.md#memory-and-build-pins) measured 2,732-byte peak heap
after keygen/export, 16,796 bytes after the 4 KiB verifier case, and 7,216-byte
stack headroom. Full keygen/commit reached its completion screen in 1.928 s
including automated approval navigation. These are emulator measurements from
a separate metrics build; they do not establish physical timing or watchdog
behavior. Default firmware has no metrics command.

Speculos 0.27.0 needs the explicit test-only Rust NVM metadata adapter in
`tests/enable_rust_nvram.py`. Its existing C file backend preserves the actual
SDK PIC region and app NVM; the first image is initialized from the ELF rather
than zeros. Later boots reuse bytes written by the previous process. Storage
logic fault injection remains a separate native harness. Neither is physical
erase-isolation or power-loss evidence.

No Ledger was connected (`lsusb -d 2c97:` found none). App 0.2.0 installation,
OS enforcement of the narrow namespace, real key creation/reboot, flash
durability/interruption, and Gen5 resource/watchdog measurements remain gates
before implementing signing. The broader required observations are:

| Area | Evidence required from implementation |
| --- | --- |
| Derivation | Emulator agrees with the KDF vector; installed Gen5 app derives only the configured SLIP label; neighboring labels/EC derivations denied; loader TLV and C-shim status/zeroization checked |
| Creation | Both real roots computed; public ABI/commitment agrees with the reference; reject leaves EMPTY; lost response recovers the committed identity; repeated create cannot overwrite it |
| Restart | Completed key creation reloads the same public identity and counters without reinitializing them; wrong wallet/passphrase locks the record |
| NVM ordering | Confirm actual erase isolation and syscall durability; interrupt before/during/after each of the three writes and readbacks; recover only the safe committed state or LOCKED/EMPTY as defined |
| Stateful signing | All four independently verified device signatures, paths of lengths 1–4, fifth request rejected; repeated digest still consumes a new leaf |
| UI and sessions | Full key/digest/leaf review, rejection without use, immutable request during review, malformed/competing commands, stale boot/token, repeated finalize and chunk reads |
| Failure | Signing/grinding/allocation/self-check failures after reservation consume the leaf; lost output never causes reuse; cancellation/restart cannot reclaim it |
| Record validation | Bit flips, wrong MAC/profile/version, inconsistent counters/roots/commitment, zero/erased/torn marker, and exact exhaustion; no silent fallback or repair |
| Recovery boundary | Reinstall/same-mnemonic second device creates a fresh identity; coherent old-record replay remains an explicitly unsupported rollback scenario |
| Resources | Actual Gen5 keygen/sign timings, stack/heap peaks, NVM footprint/writes, USB responsiveness, and watchdog behavior against section 6 |

Run storage fault logic tests independently of the emulator. Establish whether
the pinned Speculos setup preserves this NVM across process restarts; fresh
processes with fresh state are not persistence evidence. Hardware tests must
distinguish a USB disconnect from actual power loss on the battery-powered
Gen5. Rerun acceptance on the final uninstrumented build.

The host Rust verifier is useful for differential checks but shares the device
implementation. Preserve the existing Solidity-derived vectors and pin an
independent verifier for device-produced outputs before claiming independent
cryptographic acceptance. Selecting and running that verifier, physical NVM
fault evidence, and performance measurements belong to implementation work.
