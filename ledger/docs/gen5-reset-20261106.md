## Observation tools and offline review

The [recorder](../hardware/README.md) flushes/fsyncs its event before each APDU,
records responses/deadlines, and keeps evidence when a process is killed or a
native read blocks. The pinned HID implementation's first read does not honor
its timeout argument. A process watchdog and outer timeout bound that case.
Launch/exit actions send no hidden follow-up query, and plain recomputation is
now separate from the busy-probe computation. Approval tokens are redacted.

The [SHRINCS Launch control](../launch-check/README.md) uses the pinned SDK and
home/exit UI without scheme code, derivation, or application NVM. Its isolation
and discovery tests passed in Speculos. The initial control build failed on
the SDK's reply type conversion, was corrected, and was tested before installation;
both build logs remain in the evidence directory.

The archived HW Check linker symbols allocate 18,472 app-stack bytes. Its
`sample_main` prologue reserves 4,064 bytes plus saved registers; `generate`
reserves 3,192 bytes plus saved registers, before nested calls. These are static
frames, not a complete maximum-stack calculation. The SDK stack painter uses
the current stack pointer and is called from main context. Its OS syscall-stack
use is outside the measurement. NBGL lifetimes and lock/exit behavior remain
audit targets; no inspected code establishes the factory-reset cause or exactly
when application execution begins relative to the unverified-app prompt.

## Pending-warning lock comparison

After the cases above, the operator selected **one-minute auto-lock**. At
14:22:15 UTC the host recorded confirmation that "Open unverified app" was
visible and untouched. The quiet interval exceeded two minutes with no USB
client or outstanding APDU (`19`–`21`). The operator reported that the warning
remained visible and Continue opened the app normally (`22`). No PIN/lock screen
or freeze was observed, so this was a pending-warning idle test; an actual
lock transition was not demonstrated.

The next isolated comparison (`23`) completed one plain recomputation with
one-minute auto-lock still enabled in **66.102503 seconds**. It returned the
same commitment, completed 260 leaves/65 event polls, performed zero writes,
preserved both NVM digests, and retained its boot nonce. Peak heap was 2,756
bytes; app stack stayed at the READY-startup high-water mark of 13,400 bytes,
leaving **5,072 bytes**. Its individual resource check passed. The ensuing host
exit (`24`) also returned success; the visible transition/reopen observation
is recorded separately.

This distinguishes a plain recomputation after restart from the complete
creation path, whose measured headroom remains a failure. Review UI, generation,
and storage have not yet been measured separately, so the extra stack use cannot
be attributed specifically to NVM or keygen. One enabled-auto-lock timing sample
also does not establish that the setting caused the shorter duration. No actual
lock during computation is established by elapsed time alone.

After the subsequent host exit, the operator initially selected "The opening
warning froze" (`25`). The follow-up confirmation answer was "The screen or
behavior is different" (`26`). They then reported the lock screen and could
not reconstruct the intervening PIN screen or timing (`27`). The operator found
the sequence difficult to follow, so the matrix was stopped. A single normal
unlock returned to the usual device home screen (`28`). No USB request or
power-button recovery followed the host exit.

**This bounded run ended without a confirmed persistent freeze, Protection
mode, or factory reset.** The earlier warning report remains ambiguous; normal
unlock does not establish what happened at the warning. The device was left at
home, and no final app-state snapshot was taken after unlock. The last verified
diagnostic state and NVM digests are from `23`, before exit. The broader matrix
is incomplete; do not treat these observations as hardware acceptance or proof
that the original incident is resolved. Future device sessions should use one
pending instruction at a time, without bundled historical questions. Offline
review of the reproducible creation-stack failure is the next useful work.
